## 1. What is Splunk?

### What
**Splunk** is a **data analytics and log management platform** that collects, indexes, searches, and visualizes **machine-generated data** in real time.

"Machine-generated data" means logs, metrics, events, and data that computers produce automatically:
- Web server access logs (`nginx.log`, `apache.log`)
- Application error logs (`app.log`, crash reports)
- Security events (failed logins, firewall blocks)
- Infrastructure metrics (CPU %, disk I/O, network traffic)
- Business events (orders placed, payments processed)

> **Name origin:** "Splunk" comes from **"sprunking"** — the exploration of caves. Just like cave explorers venture into the dark unknown, Splunk ventures into the dark, unstructured world of machine data to find meaningful insights.

> **Best analogy:** Splunk works like **Google for your logs**. Google indexes the web so you can search it instantly. Splunk indexes your machine data so you can search, analyze, and visualize it instantly — even across billions of log lines.

### Why
Without Splunk (or a similar tool), logs are:
- Scattered across dozens/hundreds of servers
- In different formats (some JSON, some plain text, some CSV)
- Accessible only by SSH-ing into each server individually
- Not searchable across systems
- Deleted when disk fills up

When something breaks at 3 AM, you'd need to SSH into 50 servers, `grep` through gigabytes of logs, and manually piece together what happened. That takes hours.

With Splunk:
- All logs flow into one central platform
- Search across all systems in seconds with SPL (Splunk Processing Language)
- Dashboards show real-time system health
- Alerts fire before users even notice a problem
- Full audit trail for compliance

### How (Simplified Flow)

```
1. Logs are generated by your applications and infrastructure
2. Splunk Forwarders collect these logs from source machines
3. Logs are sent to the Splunk Indexer (stored + indexed)
4. You search, visualize, and alert on the indexed data
```

### Impact

| With Splunk | Without Splunk |
|---|---|
| Search 1 billion log lines in seconds | SSH into servers, grep one file at a time |
| Real-time dashboards for system health | No visibility until something breaks |
| Alerts fire when anomalies occur | Find out from users/clients that something is wrong |
| Centralized security monitoring (SIEM) | Security events scattered and missed |
| Compliance reports generated automatically | Manual log collection for audits |

## 2. Splunk Architecture

### What
Splunk is built around three core components that handle different parts of the data pipeline:

```
Data Sources → Forwarders → Indexers → Search Heads → Users
```

### The Components

---

#### Data Sources
Everything that generates logs or events:
- Linux/Windows servers (syslog, event logs)
- Applications (Node.js, Python, Java apps)
- Databases (PostgreSQL, MongoDB slow query logs)
- Cloud services (AWS CloudTrail, VPC Flow Logs)
- Network devices (firewalls, routers, switches)
- Containers (Docker daemon logs)

---

#### Forwarders (Data Collection Agents)
Lightweight agents installed on source machines that **collect and forward logs** to the Indexer. Two types — covered in detail in [Section 3](#3-splunk-forwarders--universal-vs-heavy).

---

#### Indexer (The Storage Engine)
The heart of Splunk. It:
1. **Receives** data from forwarders
2. **Parses** it (identifies timestamps, source types, fields)
3. **Indexes** it (breaks into searchable tokens, like Google indexing web pages)
4. **Stores** it in compressed, time-stamped buckets on disk

Once indexed, data can be searched in milliseconds even across terabytes.

---

#### Search Head (The Interface)
The component users interact with — the **Splunk Web UI** (port 8000). It:
- Accepts SPL (Splunk Processing Language) search queries
- Distributes search queries across multiple indexers
- Returns and renders results
- Hosts dashboards, reports, and alerts

---

#### Deployment Server (Enterprise)
Centrally manages configuration and app deployment to forwarders across hundreds/thousands of machines.

### Architecture Types

| Deployment Type | When to use |
|---|---|
| **Single Instance** | Dev/test environments; all components on one machine |
| **Distributed (Multi-site)** | Production; separate indexers, search heads, forwarders |
| **Clustered** | Enterprise; indexer clusters for HA and data replication |

## 3. Splunk Forwarders — Universal vs Heavy

### What
Forwarders are **agents installed on source machines** that collect data and send it to the Splunk Indexer. There are two types:

---

### Universal Forwarder (UF)

**What:** A lightweight agent (~20MB) that does **only one thing** — collect raw data from files/ports and forward it to the indexer **without any processing**.

**Why:** Minimal resource usage on production machines. The indexer handles all parsing and processing.

**How:**
```
Source Machine
    │
    ├── monitors: /var/log/nginx/access.log
    ├── monitors: /var/log/app/*.log
    ├── monitors: syslog port 514
    │
    ▼
Packages raw log data
    │
    ▼
Sends to Splunk Indexer (TCP port 9997)
    │
(NO processing on this machine)
```

**Footprint:** ~20MB disk, <1% CPU, <50MB RAM

**Best for:** 99% of use cases — standard log collection from servers, apps, containers

---

### Heavy Forwarder (HF)

**What:** A full Splunk instance configured to act as a forwarder. It can **parse, transform, route, and filter data** before sending to the indexer.

**Why:** Sometimes you need to:
- Parse complex log formats before indexing
- Route different log types to different indexers
- Filter out sensitive data (PII) before it reaches the indexer
- Aggregate data from many Universal Forwarders and batch-send

**How:**
```
Universal Forwarders (many source machines)
    │  raw logs
    ▼
Heavy Forwarder (intermediate processing)
    │
    ├── parse log formats
    ├── mask sensitive fields (PII, passwords)
    ├── route: security logs → Security Indexer
    │          app logs → App Indexer
    │          infra logs → Infra Indexer
    ▼
Multiple Indexers (filtered, structured data)
```

**Footprint:** Full Splunk installation (~150MB+), uses significant CPU/RAM

**Best for:** Large enterprises, compliance requirements (PII masking), complex routing

---

### Side-by-Side Comparison

| Feature | Universal Forwarder | Heavy Forwarder |
|---|---|---|
| **Size** | ~20MB (lightweight) | Full Splunk install (~150MB+) |
| **Processing** | None — forwards raw data | Full parsing, filtering, routing |
| **Resource usage** | Very low (<1% CPU) | Higher (acts as mini-Splunk) |
| **Data transformation** | ❌ | ✅ |
| **PII masking** | ❌ | ✅ |
| **Multi-indexer routing** | ❌ | ✅ |
| **Best for** | Most use cases (99%) | Complex enterprise routing |
| **Typical placement** | Every source machine | Aggregation tier / DMZ |

## 4. Splunk Key Ports

### What and Why

| Port | Protocol | Purpose | When it's used |
|---|---|---|---|
| **8000** | HTTP/HTTPS | Splunk Web UI | Browser access to dashboards, search, alerts |
| **8088** | HTTP | HTTP Event Collector (HEC) | Apps send events directly via REST API (no forwarder needed) |
| **8089** | HTTPS | Splunk Management/REST API | Programmatic access, integrations, CI/CD, forwarder management |
| **9997** | TCP | Forwarder → Indexer data channel | Universal/Heavy Forwarders stream data to indexers |
| **514** | UDP/TCP | Syslog input | Network devices, Linux syslog |

### HTTP Event Collector (HEC) — Port 8088

**What:** A built-in REST API endpoint that lets any application **send events directly to Splunk** over HTTP — no forwarder agent needed.

**Why useful for DevOps:**
- Jenkins pipeline: send build start/end/fail events to Splunk via `curl`
- Node.js app: send custom business events (order placed, payment failed) directly
- Lambda function: send serverless execution logs to Splunk

```bash
# Send an event to Splunk via HEC
curl -k https://splunk-server:8088/services/collector/event \
  -H "Authorization: Splunk YOUR_HEC_TOKEN" \
  -d '{"event": "deploy_started", "app": "myapp", "version": "2.1.0"}'
```

## 5. Splunk Core Workflow — Collect → Index → Search → Alert

### Step 1: Collect (Data Ingestion)
Data enters Splunk from various sources:
- **Forwarder monitoring** — watch log files, directories
- **HEC** — apps push events via REST API
- **Syslog** — network devices on port 514
- **AWS/GCP/Azure integrations** — pull CloudTrail, VPC Flow Logs, etc.
- **Scripted inputs** — run a script, output becomes Splunk data

### Step 2: Index (Storage + Processing)
When data arrives at the indexer:
1. **Timestamp extraction** — Splunk finds the time in the log
2. **Source type recognition** — identifies if it's nginx, syslog, JSON, etc.
3. **Field extraction** — pulls out key fields (IP address, status code, username)
4. **Tokenization** — breaks text into searchable tokens
5. **Storage** — writes to time-stamped bucket on disk (compressed)

### Step 3: Search (SPL — Splunk Processing Language)

SPL is like SQL for logs. It uses a **pipe (`|`) syntax** — each command passes results to the next.

```splunk
# Basic search — find all ERROR logs in the last hour
index=myapp level=ERROR earliest=-1h

# Count errors by source
index=myapp level=ERROR | stats count BY source

# Top 10 IP addresses hitting the API
index=webserver sourcetype=nginx | top limit=10 clientip

# Error rate over time (for dashboard chart)
index=myapp level=ERROR | timechart count span=5m

# Failed login attempts (security use case)
index=auth action=failed | stats count BY user | where count > 5

# Average API response time
index=myapp | stats avg(response_time) BY endpoint
```

### Step 4: Dashboard (Visualization)
Saved searches become **panels** on a **dashboard**:
- Line charts (error rate over time)
- Bar charts (top endpoints by traffic)
- Tables (recent errors with details)
- Pie charts (log level distribution)
- Single values (current error count)
- Maps (geographic traffic distribution)

### Step 5: Alerts (Automated Notifications)

When a search condition is met, Splunk fires an alert. Covered in detail in [Section 6](#6-splunk-alerts).

## 6. Splunk Alerts

### What
An **alert** is an automated action triggered when a saved Splunk search returns results matching a condition.

> **Analogy:** Like a smoke detector — it continuously monitors and triggers an alarm when a threshold is crossed. You don't stare at the ceiling watching for smoke.

### Why
Without alerts, you're reactive — you find out about problems after users complain or after something catastrophes. Alerts make you **proactive** — you know about problems the moment they start.

### Alert Types

---

#### 1. Real-Time Alert
**What:** Triggers **immediately** the moment a matching event appears in the index.
**When:** Security incidents (failed login detected NOW), critical errors that need instant response.
```
Trigger: Every time a result matches
Use for: "Alert me the instant any SSH brute-force attempt is detected"
```

---

#### 2. Scheduled Alert
**What:** Runs a search on a **schedule** (every 5 minutes, hourly, daily) and fires if results meet the condition.
**When:** Most operational alerts — error rate checks, disk usage, SLA monitoring.
```
Trigger: Every 15 minutes — if error count > 10 in last 15 min
Use for: "Alert me if more than 10 errors per 15 minutes"
```

---

#### 3. Rolling Window Alert
**What:** Continuously checks a sliding time window.
**When:** Detecting sustained issues vs spikes.
```
Trigger: If 500 errors occur in any rolling 5-minute window
Use for: Sustained error storms, not brief spikes
```

---

#### 4. Digest Alert
**What:** Batches multiple triggered alerts into a **summary** and sends one notification.
**When:** Noisy environments where individual alerts would flood the inbox.
```
Trigger: Send daily summary of all triggered conditions
Use for: Low-urgency monitoring, daily reports
```

---

### Alert Actions (What Splunk Does When Triggered)

| Action | How |
|---|---|
| **Email** | Sends email with search results attached |
| **Slack** | Posts to a Slack channel via webhook |
| **PagerDuty** | Creates an incident for on-call engineer |
| **Webhook** | HTTP POST to any URL (custom integrations) |
| **Script** | Runs a shell script (e.g., auto-restart a service) |
| **ITSM ticket** | Creates a Jira/ServiceNow ticket |
| **SNS** | Sends to AWS SNS for fan-out notifications |

---

### Alert Severity Levels

```
LOW      → Informational — something to watch
MEDIUM   → Warning — investigate when time allows
HIGH     → Important — investigate within 1 hour
CRITICAL → Urgent — wake up the on-call engineer NOW
```

## 7. Docker vs Docker Compose

### What

**Docker** runs individual containers — one command, one container.

**Docker Compose** manages **multiple containers** that work together as an application stack — defined in a single YAML file (`docker-compose.yml`), started with one command.

### Why Docker Compose?

A real application is almost never just one container. A typical Node.js app needs:
- Container 1: Node.js API server
- Container 2: PostgreSQL database
- Container 3: Redis cache
- Container 4: Nginx reverse proxy

Without Compose: run 4 separate `docker run` commands with all their flags, networking, volumes, and environment variables. Forget one flag and nothing works.

With Compose: define everything in one YAML file. Run `docker-compose up -d`. Done.

### How — Docker Compose File Structure

```yaml
# docker-compose.yml
version: '3.8'

services:
  app:                          # Container 1: Node.js app
    image: node:20-alpine
    ...
  database:                     # Container 2: PostgreSQL
    image: postgres:15
    ...
  cache:                        # Container 3: Redis
    image: redis:7-alpine
    ...

networks:
  appnet:                       # Shared network (containers talk by service name)

volumes:
  pgdata:                       # Persistent storage for DB
```

### Core Compose Commands

```bash
docker-compose up -d          # start all containers in background
docker-compose down           # stop and remove containers
docker-compose down -v        # stop + remove containers AND volumes (data deleted)
docker-compose ps             # list running containers
docker-compose logs -f        # follow all container logs
docker-compose logs -f app    # follow just one service's logs
docker-compose exec app sh    # open shell inside 'app' container
docker-compose restart app    # restart one service
docker-compose pull           # pull latest images
docker-compose build          # rebuild images from Dockerfile
```

### Impact

| With Docker Compose | With raw Docker commands |
|---|---|
| One YAML file defines entire stack | Multiple long `docker run` commands |
| `docker-compose up` starts everything | Must run each container manually |
| Container names used as hostnames | Must manage IP addresses or custom networks |
| Shared volumes/networks auto-configured | Manual `--network` and `-v` flags |
| Version-controlled in Git | Commands exist only in someone's memory |

## 8. Docker Swarm vs Kubernetes vs OpenShift

### What — The Orchestration Landscape

When you move from running containers on one machine to running them across many machines (a cluster), you need an **orchestrator** — software that manages where containers run, how they scale, and how they recover from failures.

| | Docker Swarm | Kubernetes | OpenShift |
|---|---|---|---|
| **Made by** | Docker Inc. | Google (CNCF) | Red Hat (IBM) |
| **Complexity** | Simple | Complex | Most complex |
| **Scale** | Small-medium | Large-scale | Enterprise |
| **Cloud-native** | ❌ | ✅ | ✅ |
| **Industry standard** | ❌ (declining) | ✅ (dominant) | ✅ (enterprise) |
| **Setup time** | Minutes | Hours-Days | Days |
| **Community** | Small | Massive | Enterprise |
| **Best for** | Simple multi-host | Most production use cases | On-premise enterprise |

---

### Docker Swarm

**What:** Docker's built-in clustering tool. Extends Docker Compose concepts to multiple machines.

**Why it exists:** Simple alternative to Kubernetes when you don't need all of K8s' complexity.

**Current status:** Largely **replaced by Kubernetes**. Many companies that used Swarm have migrated to K8s. Docker Compose is still widely used for **local development** — Swarm less so.

```
Swarm cluster:
Manager Node (orchestrates)
    ├── Worker Node 1 (runs containers)
    ├── Worker Node 2 (runs containers)
    └── Worker Node 3 (runs containers)
```

---

### Kubernetes

**What:** The industry-standard container orchestration platform. Manages containers across a cluster of machines — scheduling, scaling, healing, networking, storage.

**Why it dominates:**
- Backed by Google (battle-tested at Google scale)
- CNCF-governed (vendor-neutral)
- Every major cloud has a managed K8s service (EKS, GKE, AKS)
- Massive ecosystem (Helm, Istio, Argo CD, etc.)
- Rich feature set: rolling updates, autoscaling, self-healing, secrets, config maps

**When to choose:** Almost always in production for medium-to-large applications.

---

### OpenShift

**What:** Red Hat's enterprise Kubernetes distribution. It's Kubernetes + extra enterprise features (built-in CI/CD, developer tools, stricter security policies, support contracts).

**Why it exists:** Some enterprises need:
- Official Red Hat support (24/7 SLA)
- On-premise deployment with enterprise security
- Integrated developer portal and pipelines
- Compliance certifications (FIPS, Common Criteria)

**Key differences from vanilla K8s:**
- Built-in CI/CD (OpenShift Pipelines based on Tekton)
- Stricter security (pods can't run as root by default)
- Built-in container registry
- Developer-friendly web console
- **Managed by Red Hat, not cloud providers**

**When to choose:** Large enterprises with on-premise requirements, regulated industries (banking, healthcare, government), or those with existing Red Hat relationships.

---

### The Practical Decision

```
Starting out / local dev          →  Docker Compose
Simple multi-host (small team)    →  Docker Swarm (declining) or small K8s
Most production workloads         →  Kubernetes (EKS / GKE / AKS)
Enterprise on-premise             →  OpenShift
```

## 9. Lab Walkthrough — Splunk on EC2 via Docker Compose

### Infrastructure Setup

```
AWS EC2 Instance:
- Type: T2X Large (2 vCPU, 8GB RAM)  ← Splunk is memory-hungry
- Storage: 50GB gp2                   ← Indexer needs space for log data
- OS: Amazon Linux 2
- Security Group: open port 8000 (Splunk UI)
```

### Why T2X Large (Not T2 Micro)?
Splunk indexing is CPU and memory intensive. Running it on a T2 Micro will result in:
- Out-of-memory kills
- Very slow search performance
- Indexer unable to keep up with log ingestion

---

### Step-by-Step Lab

#### Step 1: Launch and Connect to EC2

```bash
# Launch T2X Large Amazon Linux 2 with 50GB storage
# Connect via SSH
ssh -i your-key.pem ec2-user@<EC2-PUBLIC-IP>
```

#### Step 2: Install Docker + Docker Compose

```bash
# Run the installation script
#!/bin/bash
set -e

echo "=== Installing Docker ==="
sudo yum update -y
sudo yum install -y docker
sudo systemctl start docker
sudo systemctl enable docker
sudo usermod -aG docker ec2-user

echo "=== Installing Docker Compose ==="
COMPOSE_VERSION="2.24.0"
sudo curl -L \
  "https://github.com/docker/compose/releases/download/v${COMPOSE_VERSION}/docker-compose-$(uname -s)-$(uname -m)" \
  -o /usr/local/bin/docker-compose
sudo chmod +x /usr/local/bin/docker-compose

echo "Docker: $(docker --version)"
echo "Compose: $(docker-compose --version)"
```

#### Step 3: Create `docker-compose.yml` for Splunk

```bash
mkdir splunk-lab && cd splunk-lab
nano docker-compose.yml
```

#### Step 4: Start Splunk

```bash
docker-compose up -d
# Wait ~60 seconds for Splunk to initialize
docker-compose logs -f splunk   # watch startup logs
```

#### Step 5: Open Security Group Port 8000

```
AWS Console → EC2 → Security Groups → Edit Inbound Rules
Add:
  Type: Custom TCP
  Port: 8000
  Source: 0.0.0.0/0 (or your IP for security)
```

#### Step 6: Access Splunk UI

```
Browser: http://<EC2-PUBLIC-IP>:8000
Username: admin
Password: (set in docker-compose.yml as SPLUNK_PASSWORD)
```

#### Step 7: What Was Demonstrated

```
Log generation    →  Simulated app logs written to a file
Data ingestion    →  Splunk monitors the file, ingests events
Search queries    →  SPL queries to find errors, count by source
Dashboard         →  Created panels with charts from saved searches
Alert config      →  Scheduled alert: email if error count > 5/minute
```

## 11. Scenario-Based Q&A

---

🔍 **Scenario 1:** Your Node.js API is deployed across 20 EC2 instances. When errors spike, the DevOps team has to SSH into each server individually and grep logs. This takes 45+ minutes to diagnose. How does Splunk solve this?

✅ **Answer:** Install a **Universal Forwarder** on each of the 20 EC2 instances. Configure it to monitor `/var/log/app/*.log` and send data to the Splunk Indexer. Now all logs from all 20 servers flow into one place. When errors spike, open Splunk and run: `index=nodeapp level=ERROR | stats count BY host` — you'll immediately see which servers are throwing errors. Total diagnosis time: **30 seconds** instead of 45 minutes. Set up a **Scheduled Alert**: if error count > 50 in 5 minutes → Slack notification → you know before users do.

---

🔍 **Scenario 2:** Your security team suspects someone is attempting to brute-force the admin login. How do you use Splunk to detect and alert on this?

✅ **Answer:** Search for failed login events: `index=auth action=failed | stats count BY src_ip | where count > 10`. This shows any IP that failed to login more than 10 times. Set this as a **Real-Time Alert** — the moment any IP hits 10 failures, Splunk fires an alert to the security team via PagerDuty. Add the offending IP to a firewall blocklist automatically via a webhook action. Splunk transforms a reactive security posture into proactive threat detection.

---

🔍 **Scenario 3:** You're running Splunk in a financial company that handles credit card data. Logs contain cardholder names and card numbers. Can logs go directly to the Splunk Indexer without violating PCI-DSS compliance?

✅ **Answer:** No — PCI-DSS requires sensitive cardholder data to be masked or removed before storage. Use a **Heavy Forwarder** in between. Configure the Heavy Forwarder with a `transforms.conf` rule that masks card numbers using regex before the data reaches the indexer: `REGEX = \d{4}-\d{4}-\d{4}-(\d{4})` → `FORMAT = XXXX-XXXX-XXXX-$1`. Now only the last 4 digits are stored. PCI-DSS compliance maintained, logs still useful for troubleshooting.

---

🔍 **Scenario 4:** Your team uses Docker Compose locally but the app needs to run in production with auto-scaling and self-healing. How do you approach this transition?

✅ **Answer:** Docker Compose is perfect for local dev — everyone runs `docker-compose up` and has the full stack. For production, the path is: (1) Convert your Docker Compose services into **Kubernetes Deployment + Service + Ingress YAMLs** (tools like `kompose` can auto-convert), (2) add Liveness and Readiness probes, (3) configure HPA (Horizontal Pod Autoscaler) for auto-scaling, (4) deploy to EKS/GKE/AKS. Your Dockerfiles stay identical — only the orchestration layer changes from `docker-compose.yml` to Kubernetes YAML manifests.

---

🔍 **Scenario 5:** You want your Jenkins pipeline to send build events (started, succeeded, failed) to Splunk for a central DevOps intelligence dashboard. You don't want to install a Splunk Forwarder on the Jenkins server. What do you use?

✅ **Answer:** Use the **HTTP Event Collector (HEC)** on port 8088. In Jenkins, add a `post{}` block in the Jenkinsfile that uses `curl` to POST events directly to Splunk's HEC endpoint with a token. No forwarder needed — the pipeline pushes events directly. Build a Splunk dashboard showing: deployment frequency, success rate, average build time, most failing jobs. This is a classic **DORA metrics** implementation.

---

🔍 **Scenario 6:** Your Splunk dashboard shows a sudden spike in 500 errors at 2:47 AM on your Node.js API. How do you investigate using SPL?

✅ **Answer:** Start broad, narrow down:
```splunk
# Step 1: See all errors around the spike time
index=nodeapi status=500 earliest="2:40" latest="3:00"

# Step 2: Which endpoints are failing?
index=nodeapi status=500 earliest="2:40" latest="3:00"
| stats count BY endpoint

# Step 3: What's the error message?
index=nodeapi status=500 earliest="2:40" latest="3:00" endpoint=/api/payment
| table _time, error_message, user_id, request_id

# Step 4: Correlate with deployment events
index=jenkins earliest="2:30" latest="3:00"
| table _time, job_name, status
```
You'll likely find a deployment at 2:45 AM introduced the bug. The request_id lets you trace the exact failed requests. Root cause identified in under 5 minutes.

## 12. Interview Q&A

---

**Q1. What is Splunk and how does it differ from traditional monitoring tools like Nagios or Prometheus?**

**A:** Splunk is a **data analytics and log management platform** — it collects, indexes, and analyzes machine-generated data (logs, events, metrics) from any source. Traditional monitoring tools like Nagios monitor infrastructure metrics (is the server up? is CPU high?) with predefined checks. Prometheus collects time-series metrics. Splunk is broader: it ingests unstructured logs, metrics, and events, lets you search them with SPL, build custom dashboards, and create alerts on any pattern — not just predefined thresholds. Splunk is especially powerful for log correlation across many systems and security analytics (SIEM).

---

**Q2. What is the difference between a Universal Forwarder and a Heavy Forwarder in Splunk?**

**A:** A Universal Forwarder is a lightweight (~20MB) agent that collects raw log data from a source machine and forwards it as-is to the Splunk Indexer — no processing. It's suitable for 99% of use cases with minimal resource impact. A Heavy Forwarder is a full Splunk installation configured as an intermediate data processor. It can parse, transform, mask sensitive data, filter, and route logs to different indexers before they're stored. Use Heavy Forwarders when you need PII masking for compliance, complex routing to multiple indexers, or aggregating data from many Universal Forwarders.

---

**Q3. What is the HTTP Event Collector (HEC) in Splunk and when would you use it instead of a forwarder?**

**A:** HEC is a REST API endpoint (port 8088) built into Splunk that allows applications to push events directly over HTTP without installing a forwarder agent. Use HEC when: the source is ephemeral (Lambda functions, containers that start and stop), you can't install an agent, you want applications to send custom business events (not just log files), or you're integrating CI/CD tools like Jenkins to report build events. HEC uses token-based authentication and accepts JSON events in a simple POST request.

---

**Q4. What is Docker Compose and how does it differ from Kubernetes?**

**A:** Docker Compose manages multiple containers on a **single machine** using a YAML file — ideal for local development. `docker-compose up` starts all containers with their networks, volumes, and environment variables configured. Kubernetes manages containers across a **cluster of machines** with auto-healing, auto-scaling, rolling deployments, and high availability. Docker Compose is simple but has a single point of failure (one machine). Kubernetes is complex but production-grade. Common pattern: Docker Compose for local dev, Kubernetes for production.

---

**Q5. What are the different types of alerts in Splunk?**

**A:** Splunk supports four main alert types: (1) **Real-time alerts** — trigger immediately when a matching event appears, used for critical security or error events. (2) **Scheduled alerts** — run a search on a schedule (every 5 minutes, hourly) and alert if conditions are met, the most common type for operational monitoring. (3) **Rolling window alerts** — continuously check a sliding time window, good for detecting sustained issues vs brief spikes. (4) **Digest alerts** — batch multiple triggered conditions into a summary notification, reducing alert fatigue in noisy environments.

---

**Q6. How does Splunk's indexing work and why is it similar to how Google works?**

**A:** Both Splunk and Google solve the same problem: how to search enormous amounts of unstructured text in milliseconds. Google crawls web pages, breaks them into tokens, and stores an inverted index (word → list of pages containing it). When you search, Google looks up your query in the index instantly. Splunk does the same with log data: when a log event arrives, it's broken into tokens (words, field values, timestamps), and an inverted index is built. When you search SPL, Splunk looks up the index rather than scanning every raw log — making searches over terabytes of data return in seconds.

---

**Q7. What is OpenShift and how does it differ from vanilla Kubernetes?**

**A:** OpenShift is Red Hat's enterprise Kubernetes distribution. It's Kubernetes under the hood, but adds: built-in CI/CD pipelines (OpenShift Pipelines via Tekton), a developer portal and web console, stricter security defaults (containers can't run as root by default), a built-in container registry, and official Red Hat support with SLAs. Key differences: OpenShift has an opinionated, more secure setup out of the box; vanilla K8s is more flexible but requires more configuration. OpenShift is typically chosen by regulated industries (banking, healthcare) and enterprises with existing Red Hat contracts needing on-premise deployment.

---

**Q8. What SPL query would you write to find the top 5 endpoints with the highest error rate in the last 24 hours?**

**A:**
```splunk
index=webserver status>=400 earliest=-24h
| stats count AS total_requests,
        count(eval(status>=500)) AS server_errors
  BY endpoint
| eval error_rate = round((server_errors / total_requests) * 100, 2)
| sort -error_rate
| head 5
| table endpoint, total_requests, server_errors, error_rate
```
This calculates error rate per endpoint, sorts descending, and shows the top 5 worst offenders — a typical dashboard panel for API health monitoring.

---

**Q9. Why is T2X Large recommended for running Splunk? What happens on smaller instances?**

**A:** Splunk's Indexer performs CPU-intensive parsing, field extraction, and tokenization on every event. Search operations run in-memory for performance. On a T2 Micro (1 vCPU, 1GB RAM): the indexer struggles to keep up with incoming data (backpressure builds up), searches take minutes instead of seconds, and Java heap exhaustion causes the process to crash. T2X Large (2 vCPU, 8GB RAM) gives Splunk enough headroom for the indexer and search head to run simultaneously. For production with high log volumes, dedicated instances with SSD storage and 16+ GB RAM are recommended.

### Example 3: Node.js — Send Events to Splunk HEC

```javascript
// splunk-logger.js
// Sends structured log events to Splunk via HTTP Event Collector

const https = require('https');
const http = require('http');

class SplunkLogger {
    constructor(options = {}) {
        this.hecUrl    = options.hecUrl    || process.env.SPLUNK_HEC_URL;
        this.token     = options.token     || process.env.SPLUNK_HEC_TOKEN;
        this.source    = options.source    || 'nodejs-app';
        this.sourceType = options.sourceType || 'json';
        this.index     = options.index     || 'main';
    }

    async send(event, severity = 'INFO') {
        const payload = {
            time: Date.now() / 1000,      // Splunk uses epoch seconds
            host: process.env.HOSTNAME || 'local',
            source: this.source,
            sourcetype: this.sourceType,
            index: this.index,
            event: {
                severity,
                environment: process.env.NODE_ENV,
                ...event
            }
        };

        return fetch(`${this.hecUrl}/services/collector/event`, {
            method: 'POST',
            headers: {
                'Authorization': `Splunk ${this.token}`,
                'Content-Type': 'application/json'
            },
            body: JSON.stringify(payload)
        });
    }

    info(message, data = {})  { return this.send({ message, ...data }, 'INFO'); }
    warn(message, data = {})  { return this.send({ message, ...data }, 'WARN'); }
    error(message, data = {}) { return this.send({ message, ...data }, 'ERROR'); }
}

// Usage in Express app:
const splunk = new SplunkLogger();

// Log API request
app.use(async (req, res, next) => {
    const start = Date.now();
    res.on('finish', () => {
        splunk.info('api_request', {
            method: req.method,
            endpoint: req.path,
            status: res.statusCode,
            duration_ms: Date.now() - start,
            user_id: req.user?.id
        }).catch(console.error);
    });
    next();
});

// Log errors
app.use((err, req, res, next) => {
    splunk.error('unhandled_error', {
        message: err.message,
        stack: err.stack,
        endpoint: req.path,
        method: req.method
    }).catch(console.error);
    res.status(500).json({ error: 'Internal Server Error' });
});
```

### Example 4: Jenkins Pipeline — Send Build Events to Splunk

// Jenkinsfile with Splunk HEC integration
pipeline {

            }
        }

            }
        }

            steps {
                sh './scripts/deploy.sh production'
            }
        }

            """
        }
    }
}
