# JWT

JSON Web Tokens (JWTs) are the standard for authorizing requests in modern APIs and microservices. However, a poor understanding of JWT security can lead to critical vulnerabilities, such as using weak signing keys, storing sensitive data (like passwords) in the unencrypted payload, or exposing tokens to Cross-Site Scripting (XSS) attacks.

### The Structure of a JWT
A JWT is a string divided into three parts separated by dots (`.`):
1. **Header**: Declares the token type (`JWT`) and the signing algorithm used (e.g. `HS256` or `RS256`).
2. **Payload**: Contains the claims (user data and token metadata like user ID, roles, and expiration timestamp `exp`).
3. **Signature**: A hash generated by taking the base64-encoded Header and Payload, combining them with a secret key, and running them through the declared algorithm. This verifies that the token was not altered in transit.

*Important*: The Header and Payload are base64url-encoded strings, **not encrypted**. Anyone can decode a JWT and read the payload. Never store sensitive secrets (like passwords or API keys) inside a JWT payload.

### Symmetric vs. Asymmetric Signing
* **Symmetric Signing (e.g. HS256)**: Uses a single **Shared Secret Key** to both sign and verify the token. Every microservice that needs to verify the token must have access to this secret key. If one service is compromised, attackers can sign fake tokens for the entire system.
* **Asymmetric Signing (e.g. RS256)**: Uses a **Private Key** (kept secure on the authorization server) to sign tokens, and a corresponding **Public Key** (distributed freely) to verify them. Other services can verify tokens using the public key without needing the private key, improving security.

## Deep Dive

### Security Vulnerabilities and Mitigation
* **Token Storage**: Storing JWTs in browser `localStorage` makes them vulnerable to **XSS (Cross-Site Scripting)** attacks, where malicious scripts extract the token. Storing them in **HttpOnly Cookies** prevents script access, but exposes them to **CSRF (Cross-Site Request Forgery)** attacks. Mitigate CSRF by using `SameSite=Strict` cookie settings.
* **Algorithm Manipulation**: Old libraries had a vulnerability where attackers could change the header algorithm to `"none"`. This caused the library to skip signature verification, accepting fake payloads. Modern libraries reject the `"none"` algorithm by default.

## Visual Explanation

### JWT Layout and Signature Verification
```text
Encoded JWT:
[ xxxxx.yyyyy.zzzzz ]
   │     │     │
   │     │     └── Signature: HMACSHA256(base64(Header) + "." + base64(Payload), Secret)
   │     └──────── Payload: Contains claims { "sub": "12345", "role": "admin" }
   └────────────── Header: Declares algorithm { "alg": "HS256", "typ": "JWT" }

Client Request Header:
Authorization: Bearer xxxxx.yyyyy.zzzzz

Verification Process (Server-Side):
1. Re-compute Signature using local Secret.
2. Compare re-computed signature with signature segment ('zzzzz') sent by client.
3. If they match and the token has not expired ('exp'), the request is authorized.
```

## Real-World Example
Consider an e-commerce API. When a user logs in, the authentication server signs a JWT containing the user's ID and roles, and returns it. For subsequent API requests (like adding items to a cart), the client sends the JWT in the `Authorization` header. The resource server verifies the token locally using the shared public key, processing the request without querying the user database, which improves API performance.

## Code Examples

### Sign, Verify, and Express Authorization Middleware

```javascript
// middleware/auth.js
// Dependency required: npm install jsonwebtoken
const jwt = require('jsonwebtoken');
const AppError = require('../utils/AppError');

const JWT_SECRET = process.env.JWT_SECRET || 'super-long-secure-and-private-secret-key-123';

// 1. Helper to sign new tokens
const signToken = (payload) => {
  return jwt.sign(payload, JWT_SECRET, {
    algorithm: 'HS256',
    expiresIn: '1h' // Token expires after 1 hour
  });
};

// 2. Middleware to protect routes and verify JWTs
const protectRoute = (req, res, next) => {
  let token;

  // Read token from Authorization header (Bearer token pattern)
  const authHeader = req.headers.authorization;
  if (authHeader && authHeader.startsWith('Bearer')) {
    token = authHeader.split(' ')[1];
  }

  if (!token) {
    return next(new AppError('Unauthorized: Access token is missing.', 401));
  }

  try {
    // Verify token signature and expiration
    const decodedPayload = jwt.verify(token, JWT_SECRET);
    
    // Attach verified user context to the request object
    req.user = {
      id: decodedPayload.id,
      role: decodedPayload.role
    };

    next();
  } catch (err) {
    if (err.name === 'TokenExpiredError') {
      return next(new AppError('Unauthorized: Access token has expired.', 401));
    }
    return next(new AppError('Unauthorized: Invalid token signature.', 401));
  }
};

module.exports = { signToken, protectRoute };
```

```javascript
// app.js
const express = require('express');
const { signToken, protectRoute } = require('./middleware/auth');

const app = express();
app.use(express.json());

// Login route (returns token on success)
app.post('/api/login', (req, res) => {
  const { email, password } = req.body;
  
  // Simulate database authentication check...
  if (email === 'admin@db.com' && password === 'password123') {
    const token = signToken({ id: 101, role: 'admin' });
    return res.json({ token });
  }

  res.status(401).json({ error: 'Invalid credentials' });
});

// Secure route (requires valid JWT)
app.get('/api/dashboard', protectRoute, (req, res) => {
  res.json({
    message: 'Secure dashboard data',
    userContext: req.user
  });
});

app.listen(3000, () => console.log('JWT Server running on port 3000'));
```

## Best Practices
* **Keep Expirations Short**: Set short expiration windows (e.g. 15 minutes) on access tokens to minimize the impact if a token is stolen. Use longer-lived, database-tracked **refresh tokens** to issue new access tokens.
* **Never store sensitive data in Payload**: Do not include sensitive information (like passwords, addresses, or phone numbers) in the JWT payload.
* **Use Strong Secret Keys**: Always use a cryptographically strong, random secret key at least 256 bits long for symmetric signing, and protect it using environment variables.
* **Use Asymmetric Keys for Microservices**: Use RS256 or ES256 asymmetric keys in microservice environments so services can verify tokens using public keys without needing access to the signing private key.

## Interview Questions

**Q:** What are the three parts of a JSON Web Token (JWT)?

> **Answer:**
> A JWT consists of three parts separated by dots: the **Header** (defines token type and signing algorithm), the **Payload** (contains the user claims and metadata), and the **Signature** (verifies that the token has not been altered).

**Q:** Can a user modify their role in a JWT to gain admin access? Why or why not?

> **Answer:**
> A user can decode the base64-encoded payload and change their role, but doing so invalidates the signature. The server verifies the signature using its private secret key when receiving the token. If the payload has been modified, the computed signature will not match the token's signature segment, and the server will reject the request as unauthorized.

**Q:** Compare symmetric signing (HS256) and asymmetric signing (RS256) for JWTs. In what scenarios is RS256 required?

> **Answer:**
> HS256 uses a single shared secret key for both signing and verification. If a resource server needs to verify a token, it must have access to this secret key, which creates a security risk in multi-tenant or distributed architectures.
> RS256 uses a private key to sign tokens and a public key to verify them. This is required in enterprise identity provider (IdP) systems and microservice architectures, where only the authentication service needs access to the private key, and external microservices can verify tokens using the public key securely.

**Q:** How would you implement a token revocation system (blacklisting) in a stateless JWT architecture to invalidate a compromised user token before it expires?

> **Answer:**
> By design, JWT verification is stateless: if the token has a valid signature and is not expired, it is accepted.
> To support token revocation without losing the benefits of statelessness:
> 1. Add a unique identifier claim (e.g. `jti` - JWT ID) to the token payload when signing it.
> 2. When a user logs out, resets their password, or a token is reported stolen, store the `jti` in a fast, in-memory cache (like Redis) with a TTL (Time To Live) set to the remaining expiration duration of the token.
> 3. Update your verification middleware to check if the incoming token's `jti` exists in the Redis blacklist. If found, reject the token as unauthorized.
> This hybrid approach preserves stateless validation for the majority of requests, while using a fast cache lookup to support instant revocation.
